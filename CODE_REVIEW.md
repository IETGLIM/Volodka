# Отчёт по архитектурному аудиту проекта VOLODKA RPG

**Дата анализа:** 5 июня 2026  
**Версия проекта:** 3.0.0  
**Объём кода:** 308 файлов, ~114 тыс. строк  
**Технологический стек:** React 19 + Vite 6 + Three.js 0.172 + Rapier 2.2 + Zustand 5

---

## Введение

Проект **Volodka RPG** — это амбициозная киберпанк-RPG с большим объёмом кода (~114 тыс. строк), построенная на **React 19 + Three.js + Rapier Physics**. Архитектура демонстрирует **сильные инженерные решения** в области разделения ответственности и управления сложностью, но имеет **критические проблемы с производительностью, масштабируемостью и документацией**, которые должны быть адресованы в приоритетном порядке.

## 2. Архитектурные паттерны

### 2.1 Управление состоянием: Zustand + Slice Pattern

**Сильные стороны:**
- ✅ **Модульная архитектура слайсов** (`createPlayerSlice`, `createExplorationSlice` и т.д.) позволяет изолировать логику по доменам
- ✅ **Типобезопасность** через TypeScript интерфейсы и переиспользуемые типы
- ✅ **API совместимость** — новая многослойная архитектура слайсов сохраняет публичный API с монолитным хранилищем
- ✅ **Ленивая инициализация** — `getGameStore()` для доступа вне React

**Слабые стороны:**
- ❌ **Отсутствие документации** к API контрактам слайсов
- ❌ **playerSlice переполнен** — содержит 80+ методов (1059 строк), смешивает проверки, вычисления и мутации
- ❌ **Нет селекторов** — компоненты читают всё хранилище, перерисовываясь на любое изменение состояния
- ❌ **Отсутствие нормализации** данных (quests, NPCs, items — хранятся как вложенные массивы)

### 2.2 Организация 3D-рендера: React Three Fiber + Error Boundaries

**Архитектура (RPGGameCanvas.tsx):**
- 🛡️ **Canvas3DErrorBoundary** — перехватывает ошибки R3F с auto-retry
- 🛡️ **PhysicsErrorBoundary** — fallback на SimplePlayer если Rapier WASM не загружается
- 🛡️ **PostFXErrorBoundary** — отключает пост-обработку если WebGL не готов

**Сильные стороны:**
- ✅ **Отказоустойчивость** — игра работает без физики, без пост-обработки (graceful degradation)
- ✅ **Модульная иерархия компонентов** — сцены, камера, NPC, частицы разделены
- ✅ **Динамические материалы** — система погоды, эффекты применяются через слои

**Проблемы:**
- ❌ **Монолитный Canvas** — 585 строк, импортирует 50+ компонентов в исходном виде (не через React.lazy)
- ❌ **Утечки памяти потенциальны** — `useThreeCleanup` крайне спасающий, но не гарантирует очистку текстур
- ❌ **DPR управляется вручную** — `useDynamicDPR` требует явного вызова
- ❌ **Отсутствие мипмапов/тайлинга** для 3D моделей — каждая сцена загружает полные модели

### 2.3 Система игровых событий: Event Bus + Deduplication

**EventBus.ts** (266 строк) реализует типизированный pub/sub с **payload-aware дедупликацией**:
- Ключ dedup: `${event}:${JSON.stringify(payload)}`
- Окно dedup: 500ms (предотвращает спам)
- DEDUP_EXEMPT: события боевой системы, взаимодействия (всегда пропускают dedup)
- Ленивая очищение: таймер запускается при первой эмиссии

**Сильные стороны:**
- ✅ **Типобезопасность** через `EventMap`
- ✅ **Предотвращение дублей** с граммотной граничной логикой
- ✅ **Debug режим** для трассировки событий

**Проблемы:**
- ❌ **Отсутствие приоритизации** — все слушатели срабатывают в случайном порядке
- ❌ **Отсутствие отписки по шаблону** — нужно хранить обработчик для `off()`
- ❌ **Используется только на границе слоёв** (хорошо) но документация не ясна где именно

### 2.4 Orchestrator-паттерн: Огромные кастомные хуки

**Проблема существует:** `useAudioOrchestrator.ts` (747 строк), `useInteractionOrchestrator.ts` (516 строк) содержат **исходный код внутри функции**, а не модульное разделение.

**Влияние на масштабируемость:**
- ❌ Хуки невозможно модульно тестировать
- ❌ Сложность читаемости: нужно перемещаться на 747 строк для логики
- ❌ Переиспользование невозможно (copy-paste код)

## 3. Производительность

### 3.1 Bundle Size & Code Splitting

**Конфигурация (vite.config.ts):**
```typescript
manualChunks: {
  three: ['three', '@react-three/fiber', '@react-three/drei', '@react-three/postprocessing', '@react-three/rapier'],
  vendor: ['react', 'react-dom', 'zustand', 'framer-motion'],
}
```

**Анализ:**
- ✅ **Хорошее разделение** — Three.js отделён от основного приложения
- ✅ **Верс. вендоров** — React 19, Zustand 5 без альтернатив
- ⚠️ **Отсутствует** разделение UI панелей (Tier 2/3)

**Проблемы:**
1. **Контент вложен в бандл**: `data/` (750 КБ) полностью включён в основной чанк
2. **GameOrchestrator содержит 40+ панелей** — dev сервер OOM при лёнивой загрузке
3. **Отсутствие tree-shaking** для неиспользуемого контента

### 3.2 Three.js оптимизация

**Критические проблемы:**
1. **Отсутствие LoD (Level of Detail)** для NPC и окружения
2. **Нет переиспользования текстур** между сценами, нет кэширования
3. **Нет явного dispose()** на смену сцены для геометрий и материалов

### 3.3 Управление памятью

- `useThreeCleanup.ts` — пытается удалять материалы/геометрии
- ❌ **Неполное:** не очищает текстуры, буферы вершин, рендертекстуры пост-обработки
- Потенциальные утечки в Web Audio API и EventBus listeners

## 4. Масштабируемость

### 4.1 Модульность и связанность

**Хорошее:**
- ✅ `engine/` отделён от `components/` — логика игры независима от UI
- ✅ `data/` полностью статична — легче расширять контент
- ✅ `shared/types/` глобальные типы предотвращают циклические зависимости

**Проблемы:**
1. **Tight coupling в компонентах:** `HUD.tsx` (1283 строки) импортирует: eventBus, gameStore, questStore, SCENE_CONFIG и т.д. — 15+ импортов
2. **Циклические зависимости потенциальны:** `gameStore → playerSlice → eventBus → [потребители eventBus]`
3. **Отсутствие API слоя** — компоненты напрямую мутируют gameStore

### 4.2 Добавление новых сцен

**Текущий процесс:**
1. Определить сцену в `sceneDefinitions.ts` (872 строки)
2. Запустить `sceneDefinitionGenerator.ts` для генерации `scenes.ts`
3. Создать визуальный компонент в `components/3d/[SceneName]Visual.tsx`
4. Зарегистрировать в `SceneEnvironment.tsx`

**Проблемы масштабирования:**
- ❌ Ручной процесс генерации (нет автоматизации)
- ❌ Конфиг сцен в TypeScript (не JSON) — сложнее парсить за границами приложения
- ❌ Отсутствие валидации схемы сцен

## 12. Заключение

**Volodka RPG** — это хорошо спроектированный инди-проект с **современным технологическим стеком** и **продуманной архитектурой в области разделения ответственности**. Однако проект требует **критических улучшений в области производительности, тестирования и документации** перед масштабированием.

Для того чтобы другие разработчики могли продолжить работу над проектом, **приоритет номер один** — создание архитектурной документации и добавление тестов. Код читаем и структурирован достаточно хорошо, но без карты проекта новому разработчику потребуется значительное время на освоение.

При реализации рекомендаций оценка может достичь **7.5–8.0/10**.
