## 1. Цикл сессии (каждый час, ≤ 50 минут полезной работы)

```
1. cd /home/z/my-project/repo && git fetch origin && git reset --hard origin/main
   (если origin недоступен — работать с локальным main)
2. npm ci --no-audit --no-fund (только если node_modules отсутствует/сломан)
3. Прочитать docs/HOURLY_IMPROVEMENT.md (этот файл) и docs/HOURLY_LOG.md —
   ЧТО УЖЕ СДЕЛАНО, чтобы не дублировать прошлые сессии.
4. Выбрать ОДНУ задачу из очереди приоритетов (§3). Маленький атомарный
   шаг лучше большого рефакторинга.
5. Внести правку → проверить: lint + typecheck + vitest затронутых модулей
   + validate:protected + validate:content.
6. Атомарный коммит (стиль: `feat(vX.Y.Z): …` / `fix(scope): …` / 
   `refactor(scope): …` / `perf(scope): …` / `docs(changelog): …` — русский).
7. Обновить docs/HOURLY_LOG.md (что сделано, что дальше, метрики до/после).
8. Обновить CHANGELOG.md (короткая запись сверху, стиль существующих).
9. Периодический push в origin/main, если есть доступ (токен/https).
   Нет доступа — просто коммит локально; следующий агент заберёт.
```

## 2. Правила качества (строгость кодовой базы — приоритет)

- **Малые атомарные шаги.** Один коммит = одна логическая правка с тестом.
- **Тесты обязательны** для нового поведения; правка без теста — только
  для комментариев/доков/конфига.
- **Никаких новых any, @ts-ignore, eslint-disable без обоснования** в той же строке.
- **Не добавлять зависимости** без крайней необходимости (стек заморожен).
- **Удалять мёртвый код смело** (principle «Удаляй смело лишнее» из readme),
  НО: сначала grep по всему src/ — если компонент «спит» по решению автора
  (см. CHANGELOG v4.57–4.58 «сняты с экрана, маунты удалены, код спит») —
  НЕ удалять, это осознанное решение автора о возможном возврате.
- **Не трогать то, что работает**, без измерения: сначала замер (бюджеты,
  тесты), потом правка, потом повторный замер в том же коммите.
- **Все видимые строки — русский язык.**
- Проверки перед коммитом (минимум):
  `npm run lint && npm run typecheck && npm run validate:protected && npx vitest run <затронутые> --project unit`
- При сомнениях в интерпретации — консервативный вариант: не менять.

## 4. Анти-паттерны (STOP-условия сессии)

- Сессия не двигается (3 подхода упали) → откат, отчёт, стоп.
- validate:protected упал после правки → откат, стоп сессии.
- Тесты красные после правки и не чинятся за 2 попытки → откат этого шага,
  взять следующую задачу.
- Сомнение в авторском контенте → НЕ трогать, записать вопрос в LOG.

## 7. Способы запуска (что реально работает)

1. **GitHub Actions (рекомендуется, главный способ):** workflow
   `.github/workflows/hourly-guardian.yml` уже в репозитории — schedule
   cron `17 * * * *` + ручной запуск из вкладки Actions. Требует ОДНОГО
   действия автора: сделать push репозитория на GitHub (система оживёт
   сама). GITHUB_TOKEN выдаётся Actions автоматически, прав достаточно
   для публичного репозитория. В Settings → Actions → General разрешить
   workflows писать в репозиторий (Workflow permissions → Read and write).
2. **Локально по расписанию (Linux/macOS):** `crontab -e` и строка
   `17 * * * * cd /path/to/Volodka && node scripts/hourly-guardian.mjs >> docs/guardian-cron.log 2>&1`
3. **В этой песочнице z.ai:** планировщик cron недоступен агенту напрямую;
   guardian запускается командой `npm run guardian` (или `node
   scripts/hourly-guardian.mjs`). Долгоживущий фоновый процесс невозможен —
   песочница перезапускается между сессиями; ежечасный агент в облаке
   GitHub — правильное место.
4. **LLM-сессии для творческих задач P1–P3:** запускаются автором в
   чате с этой песочницей по запросу «продолжай почасовую доработку по
   HOURLY_IMPROVEMENT.md» — агент читает контракт и LOG, берёт следующую
   задачу. Guardian держит репозиторий зелёным между сессиями.
